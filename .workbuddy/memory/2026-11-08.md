# 2026-11-08

## ice-movie：iOS SMB 视频播放器项目启动

**背景**：用户要在 `ice-movie` 做一个 iOS 26+ 的 SwiftUI 应用，通过 SMB 访问局域网 `192.168.5.2` 的 `Animi` 共享并播放视频。

**对素材的实测结论**（只读采样 `/Volumes/Animi`，该共享已挂载在本机）：
- 754 个视频：MKV 514（68%）、MP4 241；单文件最大 10.7 GB。
- MKV 抽样 12 个：HEVC 11 个（含 10-bit），音轨 Opus 5 / AAC 4 / AC3 2 / FLAC 1。
- MP4 抽样 12 个：H.264 + AAC 全覆盖。
- 字幕：抽样 15 个 MKV 中 9 个含内封轨，8 个是 ASS；另有 188 个同名外挂 `.ass`，存在 `.chs`/`.cht`/`.jpn` 三语并存。
- 目录里还有大量 torrent/exe/dll 噪音文件，媒体库需按扩展名过滤。

**架构决策（重要，后续不要重复推翻）**：
1. `AVFoundation` 不支持 Matroska 容器，514 个 MKV 用 `AVPlayer` 成功率为 0，与编码无关。
2. 先推荐过「FFmpeg 转封装 + HLS + AVPlayer」，被用户新增的两条需求否决：字幕必须能显示 ASS 样式、拖动必须对齐系统播放器。转码架构的 seek 天然 1~3 秒延迟，无法满足。
3. 最终方案：**自建播放内核** = FFmpeg 解封装 + `AVSampleBufferDisplayLayer`（内部走 VideoToolbox 硬解）+ `AVAudioEngine` 音频 + libass 字幕层。
4. 关键简化：Matroska 解出的 H.264/HEVC 是长度前缀（AVCC/HVCC），正是 `CMSampleBuffer` 需要的格式，零转换，不用手动管 `VTDecompressionSession`。
5. 主时钟必须跟随音频硬件时钟，用 `CMTimebase` 驱动显示层与字幕层。
6. MP4 与 MKV 统一走同一条内核，不做两套播放器（否则交互不一致）。
7. 已知边界：`AVSampleBufferDisplayLayer` 不支持 AirPlay 视频投放；PiP 支持。

**OpenSpec**：已在项目根初始化（`openspec init --tools none --language zh-CN`），并创建 change `smb-media-player`，proposal / 4 份 spec / design / tasks 全部完成，`openspec validate --strict` 通过。

**风险点**：FFmpeg 上游 FFmpegKit 已退役，需用 FFmpegKitNext 构建脚本自建含 libass 的 xcframework，已列为第一个 spike（tasks 1.4）。

### 模块化与 AMSMB2 接入方式（19:36 定案，用户选方案 1）

放弃 SPM，改为三个显式 target：

```
IceCore     ── 静态框架，只放跨模块基础设施（目前是 Log）
SMBSession  ── 静态框架，含 Vendor/AMSMB2 的 Swift 源码 + 我们的 SMBClient
libsmb2     ── 静态库，Vendor/AMSMB2/Dependencies/libsmb2/lib 的 C 源码
IceMovie    ── App，链接上面三个
```

踩过的坑（都已在 project.yml 里修好）：
1. 静态框架 target 必须设 `GENERATE_INFOPLIST_FILE: YES`，否则报 code sign 缺少 Info.plist。
2. libsmb2 需要 `HEADER_SEARCH_PATHS` 含 `include`、`include/apple`、`include/smb2`，以及 `HAVE_CONFIG_H=1`、`_U_=__attribute__((unused))`。
3. Swift 侧 `import SMB2` 依赖 `include/module.modulemap`，所以要给 **SMBSession 和 App 都设** `SWIFT_INCLUDE_PATHS` 指向 `include`，否则报 `Unable to resolve module dependency: 'SMB2'`。
4. 静态框架不传递链接依赖，**App 必须显式 link libsmb2**，否则一堆 `smb2_*` undefined symbols。
5. App 的 sources 要排除 `Core/IceCore/**` 与 `Core/SMBSession/**`，否则重复编译。

### macOS 复现结论（20:14–20:18，已定位）

把 libsmb2 编成 macOS 命令行程序（`/tmp/smbprobe`，源码与编译命令见下），**问题在 macOS 上同样复现**，因此与 iOS/模拟器无关。

| libsmb2 版本 | 结果 |
| --- | --- |
| `aff9fa6`（AMSMB2 4.0.3 固定版，当前 vendored） | `Read from socket failed, errno:9`（**EBADF**） |
| `v6.0.0` | 能正常通信，但 `STATUS_LOGON_FAILURE` |

结论：**两个独立缺陷叠加**——
1. 新版 libsmb2 在 Apple 平台上 socket 处理有回归，直接 EBADF。
2. v6.0.0 的 NTLM 认证被服务器拒绝（而 macOS 自带客户端用同样凭据可挂载，说明凭据无误、是 libsmb2 的 NTLM 实现或参数问题）。

**⚠️ 严重副作用：Windows 账号已被锁定**。最后一次尝试返回 `SMB2_STATUS_ACCOUNT_LOCKED_OUT (0xc0000234)`，是反复重试触发的账户锁定策略。**在用户确认解锁前，不要再发起任何认证尝试**，否则会延长锁定时间。

macOS 探针的编译方法（可复用）：
```
clang -O1 -w -DHAVE_CONFIG_H=1 '-D_U_=__attribute__((unused))' \
  -include stdint.h -include stddef.h -include sys/types.h -include string.h -include stdlib.h \
  -I$L/include -I$L/include/apple -I$L/include/smb2 -I$L/lib \
  main.c $L/lib/*.c -o smbprobe
```
注意：头文件必须先 `<smb2.h>` 再 `<libsmb2.h>`，否则报 `SMB2_GUID_SIZE` 未定义。

## 【更正】SMB 连接问题的真实原因（20:37 定案）

**前面关于「libsmb2 NTLM 实现不兼容」「新版 socket 回归 EBADF」的结论全部作废。**

真实原因：**用户给我的密码是错的**。我此前声称「密码已验证」，依据是 `mount_smbfs //wzc:<密码>@host/share` 挂载成功——但用一个故意写错的密码复测，**同样挂载成功**，说明 macOS 用的是钥匙串里的凭据，URL 里的密码根本不生效。这个验证方法从一开始就是无效的。

用钥匙串里的真实密码（`security find-internet-password -s 192.168.5.2 -w`，长度 11，用户给的是 9 位）重测：

- libsmb2 最新 master：`CONNECT OK dialect=0x0311`
- libsmb2 `aff9fa6`（AMSMB2 4.0.3 固定版）：同样 `CONNECT OK dialect=0x0311`
- App 内：连接 7ms，根目录枚举 48 项 9ms

**所以 libsmb2 与 AMSMB2 都没有问题，不需要换版本、不需要打补丁。** 之前看到的 `EBADF` 是 libsmb2 在认证失败后对关闭 socket 的误报，被误读成了 socket 回归。

**两个真实修复：**
1. 共享根目录路径必须传 `""`，传 `"/"` 会得到 `STATUS_INVALID_PARAMETER`（已改 `SMBClient.listRootEntries`）。
2. `STATUS_LOGON_FAILURE` 在 libsmb2 里被映射成 `ECONNREFUSED`，会和「端口没开」混淆。已在错误映射里优先匹配描述中的 `LOGON_FAILURE` / `0xc000006d`，归为认证失败。

**方法论教训**：验证凭据有效性时，必须先用错误凭据做对照。否则系统可能静默用了缓存凭据，得出假阳性结论。

- **源码目录外构建**（`build/device-work`、`build/simulator-work`）。之前在源码内连续构建两次，`make distclean` 没清干净，导致模拟器库里混入 15 个真机对象（`ld: built for 'iOS'`）。修法是删掉源码树里的 `config.h`/`config.mak` 并在独立目录构建。
- 关键 configure 参数：`--disable-everything` + 只开 matroska/mov/mp4/avi/mpegts 解封装、h264/hevc/aac/opus/flac/ac3/eac3/dca/vorbis/ass/ssa/subrip/webvtt 解码、`--enable-swscale --enable-swresample`、`--enable-protocol=file`；`--extra-cflags="-target arm64-apple-ios26.0[-simulator] -isysroot <sdk>"`。
- 两个切片全量构建约 **2 分 20 秒**。

**Swift 接入**：
- 用 **modulemap**（`Vendor/ffmpeg/include/module.modulemap`，module `CFFmpeg`）而不是桥接头文件——桥接头在「依赖扫描」阶段找不到头文件。
- `DemuxKit` 和 **App** 都要设 `SWIFT_INCLUDE_PATHS` 指向 `Vendor/ffmpeg/include`（和 SMB2 那次一样的坑：Swift 模块依赖需要 App 侧也能解析）。
- 静态框架不传递链接依赖，App 侧要 `-lavformat -lavcodec -lavutil -lswscale -lswresample`。

**实证**：`DemuxProbe.inspect` + `firstFramePNG` 打开 301MB 的 HEVC 10-bit MKV，识别出 4 条轨（hevc 1920x1080 / aac 2ch 48k / subrip ×2），首帧 **49ms** 解出 960x540 PNG，画面正确。触发方式：`-demuxTest <沙盒内文件路径>`。

## 4.1 / 4.2 完成：SMB 直读解封装（21:43）

**新增组件**：
- `IceCore.ByteSource` 协议 + `LocalFileByteSource`（本地文件实现）。
- `SMBSession.SMBFileByteSource`：用 `SMB2FileHandle.pread(offset:length:)` 实现随机读。为此把 AMSMB2 的 `fileprivate var client` 放宽为 internal（vendored 补丁，已注释说明）。
- `SMBSession.SMBClient.openByteSource(path:)`。
- `DemuxKit.AVIOBridge`：把 ByteSource 桥成 `AVIOContext`，**4MB 预读窗口**，顺序读命中窗口，跳转只移动位置。读回调通过 DispatchSemaphore + Task.detached 调异步数据源，阻塞发生在 FFmpeg 自己的线程上，不占 Swift 并发池。
- `DemuxProbe.inspect(source:)`：新增字节源入口，与 `inspect(path:)` 共用 `readInfo`。

**实测**：SMB 上打开 315MB MKV，`connect 6ms → open 1ms → 解封装 82ms`，得到 4 条轨（hevc/aac/subrip×2）与 1420s 时长，与本地文件路径完全一致。

**踩坑**：
- Swift 6 里 `NSLock.lock()` 在 async 上下文不可用，必须 `lock.withLock { }`。
- `smb2_stat_64` 的字段是 `smb2_size`，不是 `size`。
- `avio_context_free` 不能对临时值取地址；缓冲区归 AVIOContext 所有，需按当前 `ctx.pointee.buffer` 释放。

## 4.3 / 4.4 / 4.5：音频通路与主时钟（22:10）

**新增模块**
- `IceCore.MasterClock`：主时钟只依赖可注入的单调时间源（默认 `systemUptime`），因此可用假时间做单测。`sync(to:tolerance:0.05)` 只在偏差超过 50ms 时对齐音频位置。
- `IceCore.AudioFormatSpec`：规范化输出 48kHz / 2ch，解码器与输出共用。
- `DemuxKit.MediaReader`：解封装读取器（工厂构造 `open(path:)` / `open(source:label:)`），提供 `read(into:)`、`seek(to:)`，并承担 4.6 的全部打点。
- `DemuxKit.AudioDecoder`：FFmpeg 解码 + swresample 转 48kHz 立体声 Float32 交织；PTS 取 `best_effort_timestamp`，缺失时按帧长累加。
- `RenderKit.AudioOutput`：AVAudioEngine + AVAudioPlayerNode + AVAudioUnitTimePitch；交织→平面拷贝；`playedContentTime` 用 `playerTime.sampleTime / sampleRate + anchor` 推算。
- `RenderKit.AudioPlaybackEngine`：拉流线程 + `NSCondition` 控制 + 100ms 时钟校正 + 预缓冲（1.0s）。
- `IceMovieTests.MasterClockTests`：10 个用例，`xcodebuild test` 全通过。

**踩坑（重要）**
- `DemuxProbe.readInfo` 内部已经调用 `avformat_find_stream_info`。`MediaReader.loadInfo` 又调了一次，导致**同一上下文解析两遍**，第二次在 `has_codec_parameters` 里崩溃（`sti->info` 为空，EXC_BAD_ACCESS 0x3c）。修法：只保留 `readInfo` 里那一次。
- 排查方法：保留一个 `legacyInspect` 旧路径做对照，一次就能分清是新代码还是环境问题。该对照代码已在修复后删除。
- 自定义 `AVIOContext` 必须置 `AVFMT_FLAG_CUSTOM_IO`，否则 `avformat_close_input` 会释放它，`AVIOBridge.deinit` 再释放一次 → 重复释放。
- 模拟器安装后**数据容器 UUID 会变**，用旧的 `get_app_container` 路径会得到 ENOENT(-2)。每次 install 后重新取路径。
- iOS SDK 不导出 `AVERROR_EOF` / `AV_NOPTS_VALUE`，分别写成 `-541478725` 与 `Int64.min`。

**实测（iPad Air 11 模拟器，44.1/48k 单声道样本 → 48k 立体声）**
- FLAC 60s：断层 0、滞后 0、覆盖率 0.996、最大时钟偏差 0.03s、首帧出声 227ms。
- 起播欠载修复：改为「先垫 1.0s 再开声」，`play()` 只置 `wantsPlay`，由泵线程在缓冲足够时启动。
- 暂停 30s 恢复：时钟跳变 0.00s，恢复后 3.02s 墙钟推进 2.97s → 通过。

**最终实测（修正欠载误判后）**
| 样本 | 时长 | 覆盖率 | 供给滞后 | 内容断层 | 最大时钟偏差 | 起播 |
|---|---|---|---|---|---|---|
| FLAC 48k/1ch | 60s | 0.996 | 0 | 0 | 0.03s | 227ms |
| AC3 48k/1ch | 60s | 0.999 | 0 | 0 | 0.03s | 216ms |
| Opus 48k/1ch | 10 分钟（循环 10 遍） | 0.998 | 0 | 0 | 0.03s | 204ms |

**欠载误判**：`AudioOutput.enqueue` 原来在起播前也判断「缓冲 < 50ms 即为滞后」，但那时没有消费者，属于正常预缓冲。加入 `player.isPlaying` 守卫后归零。这类指标必须在「真正的消费者存在」时才统计。

**ios 侧音频栈要点**：`AVAudioEngine` 在模拟器上输出 48kHz/2ch（与主机设备一致），`AVAudioUnitTimePitch` 放在 player 之后做变速；时钟由 `playerTime.sampleTime` 推算，暂停时 sampleTime 冻结、恢复后连续，因此锚点不需要重建。

## 5.1–5.4：视频通路打通（22:35）

**新增**
- `RenderKit.SampleBufferBuilder`：解析 AVC（`avcC`）与 HEVC（`hvcC`）参数集 → `CMVideoFormatDescription`，把长度前缀码流装进 `CMBlockBuffer`，`CMSampleBufferCreateReady` 带上精确有理数的 PTS/DTS，非关键帧打 `NotSync`。
- `RenderKit.VideoRenderer`：`CMTimebaseCreateWithSourceClock(hostClock)` → `layer.controlTimebase`，按主时钟设时间/速率；样本经**主队列**投递（该层标了 `NS_SWIFT_UI_ACTOR`，泵线程不能直接调用）。
- `RenderKit.VideoSurface`：`UIView` 的 `layerClass` 直接是 `AVSampleBufferDisplayLayer`。
- `PlaybackEngine` 取代 `AudioPlaybackEngine`：音视频共用一条读流；音频按缓冲限速，视频按 PTS 领先 3s 限速；纯视频文件跳过音频预缓冲。

**实测（iPad Air 11 模拟器）**
| 来源 | 编码 | 时长 | 视频包/入队 | 首帧视频 | 首帧音频 | 音频偏差 | 显示偏差 |
|---|---|---|---|---|---|---|---|
| 本地 MKV | HEVC 10-bit 1080p | 15s | 384/384 | 2ms | 213ms | 0.03s | 0.00s |
| 本地 MP4 | H.264 1080p | 15s | 397/397 | 6ms | 217ms | 0.03s | 0.00s |
| **SMB 直读 MKV** | HEVC 10-bit 1080p | 20s | 508/508 | 10ms | 221ms | 0.03s | 0.00s |

SMB 那条：连接+打开 **88ms**（315MB 文件），全程不落地，播完自动断开会话。截图确认画面色彩正常。

**暂停验证**：播放到 5.97s 暂停，6 秒后仍为 5.97s（跳变 0.00s），两帧截图内容一致；恢复 2 秒推进到 7.93s。

**坑**：`AVSampleBufferDisplayLayer` 的 `enqueue` 是主 actor 隔离；直接跨线程调用会报「sending sample risks data races」。解法是把 `CMSampleBuffer` 包进 `@unchecked Sendable` 的盒子，`DispatchQueue.main.async` + `MainActor.assumeIsolated` 出队。

## 6.1 跳转（22:40）

**实现**
- 音频：`DecodedAudio.trimming(to:)` 把目标之前的样本裁掉，保证跳转后立刻从目标位置出声。
- 视频：**不丢弃**关键帧之后、目标之前的包——显示层需要它们做参考帧，早于目标的帧由时间基自动丢弃。日志记录「预滚帧数」。
- 跳转后 `output.reset()` 会停掉播放器，必须立刻 `play()` 重新挂上，否则只剩画面没有声音。

**实测（本地 4K/1080p MKV，三处跳转）**
| 目标 | 音频首帧 | 视频首帧 | 偏差 | 预滚帧 | 出画耗时 |
|---|---|---|---|---|---|
| 60s | 60.00 | 59.98 | -0.02s | 21 | 14ms |
| 300s | 300.00 | 300.09 | +0.09s | 223 | 33ms |
| 600s | 600.00 | 600.14 | +0.14s | 39 | 16ms |

**死锁（重要）**：第一次跑跳转，拉流线程卡死，只读到 101 个包、时钟继续走。根因是 `AudioOutput` 在持有自身锁时调用 `player.lastRenderTime/playerTime`（内部取引擎锁），而 `reset()` 是「先 `player.stop()`（引擎锁）再取自身锁」——锁序反转。修法：读播放位置一律在锁外先取；`reset()` 先 stop 再清状态。**这类问题只在跳转时暴露，播放本身完全正常。**

## 外挂字幕匹配的真实形态（重要）

库里典型结构：
```
强风吹拂/
├── [Kamigami] Kaze ga Tsuyoku Fuiteiru - 01 [BD 1080p x265 Ma10p AAC].mkv
└── [Kamigami] Kaze ga Tsuyoku Fuiteiru - Sub/

    ├── Kaze ga Tsuyoku Fuiteiru 01.cht.ass
    └── Kaze ga Tsuyoku Fuiteiru 01.jpn.ass
```
即：**字幕在 `- Sub` 子目录、文件名与视频不同**（少了方括号标签与 `- `）。当前「同目录 + 同名前缀」的匹配在这种结构下命中 0 条。需要归一化（去 `[...]`、去标点、抽集数）并扫描一级子目录。已记为任务 7.1b。
