# Design

## Context

`MediaOrdering.areInIncreasingOrder` 目前先比较 `captureTimestamp`，最新的媒体排在前面；只有时间戳相同或都没有时才比较标题与季/集。照片目录需要这个行为，但多集剧集文件如果带 `_yyyyMMddHHmmss`，会把第 1 集排到最后。参见 proposal.md - Why。

## Goals / Non-Goals

**Goals**

- 多集剧集目录按“标题 → 季 → 集”升序，集号覆盖拍摄时间。
- 单集视频、普通视频与照片继续按时间倒序。
- 保持严格弱序，排序结果不依赖输入顺序。
- 播放队列沿用目录顺序，从第 1 集开始连播。

**Non-Goals**

- 不改变跨目录排序、搜索命中排序或收藏夹排序规则。
- 不新增季集识别规则，只清理会干扰现有识别的发布组标记。
- 不改变图片在混合网格中的时间倒序语义。

## Decisions

### D1. 目录级检测，而不是逐对忽略时间

逐对判断“两个都是剧集就忽略时间”会产生排序环：第 1 集较新、第 2 集较旧时，照片可能夹在两者之间，导致 A>B、B>C 但 A<C。改为先检测整个目录是否是多集目录，再使用一套完整的总序比较器。

检测条件：目录内至少两条视频解析出集号，且至少两条共享同一解析标题。这样不会把 `IMG_0002.MOV` 这类单条带数字的视频误判为剧集。

### D2. 剧集优先总序

多集目录使用以下分块顺序：

1. 目录
2. 剧集视频：按解析标题自然排序，再按季、集升序，最后按文件名/路径稳定排序
3. 非剧集媒体：沿用现有时间倒序 + 标题 + 文件名排序
4. 文档

分块保证严格弱序：剧集块内部不受时间影响，非剧集块继续使用原比较器，块之间固定先后。混合目录里的图片会排在剧集之后，但不会再打断集数顺序。

### D3. 自动检测，不新增调用参数

`MediaOrdering.sorted` 内部检测目录是否多集，`LibraryEntryBuilder`、收藏夹与播放队列无需改调用方式。单集目录走原有比较器，行为不变。

### D4. 排序稳定性

解析标题相同、季集相同或无法解析时，回退 `name` → `path` 的自然排序，保证跨启动和不同目录列举顺序下结果一致。

### D5. 清理 CRC 与拍摄时间后缀

真实番剧文件名常见 `[SumiSora][CLANNAD-AfterStory-][BDRip][17]...[flac_6ch](1A9723D4).mkv`：CRC `(1A9723D4)` 会留在解析标题里，使同一部剧的每一集标题都不同，多集检测无法触发。标题清理新增 8 位十六进制 CRC 组识别，并去掉保留下来的作品名方括号。另在 `MediaTitleParser.parse` 开头去掉合法的 `_yyyyMMddHHmmss` 后缀，避免 `Show - 01_2024...` 的集号因紧跟下划线而解析失败。两项都只影响标题与季集提取，不改变展示文件名或副标题日期。

## Risks / Trade-offs

- [误判普通视频为剧集] → 要求至少两集共享同一解析标题；单条带数字的视频不触发。
- [混合目录图片排到剧集后] → 只在检测到多集时发生；剧集文件夹通常没有照片，优先保证集数顺序。
- [标题解析差异导致分组不齐] → 解析标题只用于分组与排序，不改变展示标题；同组识别失败时回退原时间排序。
- [播放队列顺序变化] → 这是期望行为；从第 1 集开始连播，仍受现有过滤与跳过逻辑约束。

## Migration Plan

无数据迁移。排序在目录列举时即时计算，不缓存排序结果。
