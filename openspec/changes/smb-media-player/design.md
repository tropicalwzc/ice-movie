# Design

## Context

全新工程，无既有代码。约束来自三处，详见 proposal.md 的 Why：

**素材实测**（对测试主机 `Animi` 共享的只读采样；测试环境地址为 `192.168.5.2`，仅作夹具，不进入代码）

- 754 个视频：MKV 514、MP4 241；单文件最大 10.7 GB。
- MKV 抽样 12 个：HEVC 11 个（10-bit 为主），H.264 1 个；音轨 AAC 4 / Opus 5 / AC3 2 / FLAC 1。
- MP4 抽样 12 个：H.264 + AAC 全覆盖。
- 字幕：抽样 15 个 MKV 中 9 个含内封轨，其中 8 个为 ASS；另有 188 个与视频同名的外挂 `.ass`，存在 `.chs` / `.cht` / `.jpn` 三语并存的情况。

**平台约束**

- `AVFoundation` 不支持 Matroska 容器，与其内部编码无关；`AVPlayer` 也不支持 ASS 字幕。
- 部署目标 iOS 26.0，构建环境 Xcode 27.2 / iOS 27.2 SDK，Swift 6 严格并发。
- 模拟器无法反映 SMB 吞吐与硬解功耗，性能类结论必须在真机取得。

**依赖约束**

- 上游 FFmpegKit 已退役，预编译产物不再发布，需自行构建。
- `AMSMB2` 静态链接 libsmb2（LGPL-2.1）；libsmb2 上下文非并发安全。

**网络环境约束**

- 主机地址由路由器 DHCP 分配，日常通过局域网名称访问，**任何固定 IP 都不能成为设计假设或默认值**。
- libsmb2 的主机名解析走 `getaddrinfo`，因此 DNS 名与 `.local`（mDNS）可用；Windows 的 NetBIOS 短名在 iOS 上不保证能解析，通常需要补 `.local` 后缀或由路由器提供 DNS 解析。这一点决定了错误提示必须能区分"名称解析失败"与"主机不可达"。

## Goals / Non-Goals

**Goals:**

- MP4 与 MKV 共用一条播放路径，交互层无法感知容器差异。
- 拖动定位在 300 ms 内出画，手感对齐系统播放器。
- ASS 样式、定位与特效如实还原。
- 单活跃 SMB 会话下，浏览、播放、抽帧共享带宽而不互相阻塞。
- iPhone 与 iPad 共用一套代码与状态模型，iPad 为主要场景且具备真正适配的大屏结构，不是把手机界面放大。

**Non-Goals:**

- AirPlay 视频投放：`AVSampleBufferDisplayLayer` 不支持，且不在验收范围内。
- 服务端或本地转码、离线下载、片库刮削（海报、简介等元数据）。
- 外接显示器上的独立播放窗口、多窗口同时播放不同视频。
- 多主机并行会话：同一时刻只保持一条活跃 SMB 会话。

## Decisions

### D1 播放内核自建，不用 AVPlayer

三条路线对比后选定自建：

| 方案 | 拖动体验 | ASS 字幕 | 结论 |
| --- | --- | --- | --- |
| AVPlayer 直连 | 仅限 MP4，MKV 不可用 | 不支持 | 不可行 |
| AVPlayer + HLS 转封装 | 需现场生成分片，1~3 s 白屏 | 只能转 WebVTT，样式丢失 | 与「对齐系统播放器」冲突 |
| 自建内核 | 关键帧定位，100~300 ms | 原生支持 | 选定 |

否决 HLS 路线的关键不在实现成本，而在语义：转码架构的 seek 天然带等待，这与 specs 中「300 毫秒内呈现目标画面」无法同时成立。同理排除 MobileVLCKit 与 libmpv —— 它们能解决解码，但控件层需要重写才能与 SwiftUI 播放页统一，收益不足以抵消集成成本。

### D2 视频解码交给 AVSampleBufferDisplayLayer

不手动管理 `VTDecompressionSession`。`AVSampleBufferDisplayLayer` 接受**压缩**的 `CMSampleBuffer`，内部自行调用 VideoToolbox 完成硬解与呈现。

成立的前提是格式恰好对齐：Matroska 解出的 H.264/HEVC 码流为长度前缀格式（AVCC/HVCC），正是 `CMSampleBuffer` 所要求的封装，FFmpeg 的 `AVPacket` 数据可以直接装进 `CMBlockBuffer`，不需要 Annex-B 转换，也不需要重排 NAL。

附带收益：10-bit HEVC 的像素格式、色彩空间与 HDR 元数据由系统处理；显示层自带 `controlTimebase`，可被外部时钟驱动。

落地注意：`AVSampleBufferDisplayLayer` 在 SDK 里标了 `NS_SWIFT_UI_ACTOR`，只能在主 actor 上调用，而拉流在独立线程。样本因此经主队列投递（顺序由主队列保证），时间基由 `CMClockGetHostTimeClock()` 创建、按主时钟设一次时间与速率，只在偏差超过 100 ms 时校正。


代价：该层不暴露可合成的输出面，因此字幕不能与视频合成在同一位图里（见 D7）；不支持 AirPlay。

### D3 主时钟跟随音频硬件时钟

音频时钟是唯一不会漂移的时基。视频与字幕都以它为基准：

```
AVAudioEngine.lastRenderTime ──> CMClock/CMTimebase ──┬──> AVSampleBufferDisplayLayer.controlTimebase
                                                       └──> libass 渲染层（CADisplayLink 采样）
```

不采用视频时钟为主：音频缓冲区一旦被主动追帧就会产生可听见的断续，而视频落一两帧肉眼几乎不可察。显示层通过 `CMTimebaseSetRate` 控制播放与暂停，跳转时同步重设 `CMTimebase` 的当前时间。

落地方式：`MasterClock` 放在 `IceCore`，只依赖一个可注入的单调时间源，因此能用假时间做单元测试。`RenderKit.AudioOutput` 每 100 ms 用 `AVAudioPlayerNode.playerTime(forNodeTime:)` 的已渲染样本数换算媒体时间并据此校正。偏差小于 50 ms 时不校正，避免测量噪声让时间来回抖动；超过则直接对齐音频位置——音频是主时基，画面跟随它。

所有素材进解码器后统一转成 **48 kHz 立体声 Float32**，因此时钟推进速率与素材采样率无关，音画同步只有一套参数。

### D4 SMB 读取层用预读环与 FFmpeg 解耦

FFmpeg 的 `AVIOContext` 读回调是同步的，AMSMB2 的接口是异步的。不在 C 回调里用信号量等待异步结果 —— 一旦完成回调被派发到同一队列就会死锁。

实现分三层：

- **AVIO 回调**：只从 `AVIOBridge` 的 4 MB 窗口拷贝，缺数据时在当前 FFmpeg 线程等待一次同步读取。
- **`SMBFileByteSource`**：按 1 MB 分块向调度器提交读取，维护 24 MB（24 块）预读环；顺序读取时后台预读后续块，跳转时清空环并重置预读。
- **`SMBReadScheduler`**：单线程串行执行所有 SMB 读取，按优先级出队，避免同时向 libsmb2 句柄发起并发读取。

跳转时清空环形缓冲并取消旧预读任务。播放源保持 1 MB 块；抽帧源使用 256 KB 块，使播放请求最多等待一个较短的抽帧读取即可插队。

### D5 会话与读取调度分离，按优先级排队

libsmb2 上下文不支持并发调用。会话连接、认证、心跳与目录枚举由 `SMBClient` actor 串行化；文件读取通过共享的 `SMBReadScheduler` 单线程串行化，内部按优先级排队：**播放读取 > 预读/目录枚举 > 缩略图抽帧**。预读任务用中间优先级，播放读取可以立即插到前面。

不为不同用途开独立连接：Windows 侧对单用户并发会话有限制，且每条会话都要重新认证，与「连接稳定」的目标相悖。

### D6 缩略图走低优先级通道并复用解封装逻辑

抽帧与播放共用同一套解封装代码，但只 seek 到关键帧、解一帧、缩到 480 px 宽后落盘。优先读 MKV 内嵌 `attached_pic`，命中则完全不读视频数据。

缓存文件名取 `SHA256(路径|大小|修改时间)`，条目数超限时按最近访问时间淘汰。失败条目在本次会话内标记为不重试，避免损坏文件反复消耗带宽。

### D7 字幕以独立图层叠加，不与视频合成

`AVSampleBufferDisplayLayer` 不提供可读的输出面，无法在其上再合成字幕位图。因此 libass 渲染到独立的离屏位图，作为 `CALayer` 覆盖在视频层之上。

时间同步用 `CADisplayLink` 采样主时钟；仅在文本内容发生变化时重绘，静止帧不产生渲染开销。字号与垂直偏移通过 libass 的样式覆盖参数实现，不修改脚本本身。

### D8 FFmpeg 最小化构建，只取所需

用 FFmpegKitNext 的构建脚本产出 xcframework，但只链接 `libavformat` / `libavcodec` / `libswscale` / `libswresample`，不使用其命令行封装。

启用范围：matroska 与 mp4/mov 解封装；HEVC、H.264 解码（供抽帧与降级软解）；AAC、Opus、FLAC、AC3、EAC3、DCA、Vorbis 音频解码；ASS/SSA/SRT 字幕解码；`libass` 及其依赖 `freetype` / `fribidi` / `harfbuzz`。

关闭全部编码器（x264/x265 为 GPL，且本项目不编码），关闭网络协议与滤镜中不使用的部分，以控制包体。

### D9 凭据进钥匙串，业务数据进 SwiftData

密码是唯一进钥匙串的内容。主机地址（保存用户填写的原始字符串，见 D11）、账号、最近路径、播放进度、字幕偏好与目录索引属于结构化数据，放 SwiftData；把大量记录塞进钥匙串既慢又难查。

### D10 分层结构

```
App        ── 依赖注入、根路由、设置、菜单栏命令
Feature
  ├ LibraryKit 目录导航、标题解析、检索索引、列数计算（纯逻辑，可单测）
  ├ MediaLibrary 网格、单栈/分栏外壳、检索视图
  ├ Player     播放页、控件
  └ Shell      紧凑单栈外壳 / 常规分栏外壳，共用同一份状态模型
Core
  ├ SMBSession   会话、认证、重连、优先级队列、预读环
  ├ DemuxKit     FFmpeg 解封装封装、AVIO 桥接
  ├ RenderKit    显示层、音频输出、主时钟、A/V 同步
  ├ SubtitleKit  轨道发现、libass 渲染、样式调整
  └ ThumbnailKit 抽帧、缓存、并发调度
```

Feature 只依赖 Core 的协议，Core 之间的耦合限定在 `DemuxKit → SMBSession` 与 `RenderKit → DemuxKit` 两条边，便于单测替换。

### D11 主机以用户输入的字符串为身份，每次连接重新解析

连接记录的标识就是用户填写的原始地址串，**不缓存解析结果、不把 IP 当作身份、不内置任何默认地址**。解析发生在每次连接动作内，因此 DHCP 换址、切换网络、通过别名访问这几种情况走的是同一条路径，不需要额外分支。

这样做的代价是每次连接多一次名称解析，通常几毫秒；收益是彻底消除"换个网络就连不上"这类问题，以及避免把测试环境的 `192.168.5.2` 固化成事实上的依赖。

地址栏不做格式校验，只做非空校验 —— 用户可能填 `nas`、`nas.local`、`192.168.1.10`、甚至带 `smb://` 前缀的完整 URL，一律接受并在连接时统一归一化。解析失败与 TCP 不可达必须报不同的错：前者要提示补 `.local` 或改用 IP，后者要提示检查网络与主机电源。

### D12 布局按可用宽度分叉，状态与视图分离

iPhone 与 iPad 共用同一套状态模型（当前主机、当前目录树、当前播放项），只在视图层按实际可用宽度选择结构：

- 紧凑宽度：单栈导航，目录逐级推入。
- 常规宽度：两栏结构，左栏固定承载"主机 → 共享 → 目录"的层级，右栏承载网格或内联播放器。

关键约束是**宽度不能假设**。iPad 上应用可能以分栏、滑动覆盖、台前调度或自由缩放的窗口出现，同一个 App 运行期间会多次跨过断点。因此断点必须依据实际可用宽度而非设备型号判断，而且切换结构时不得重建状态 —— 目录内容、滚动位置、播放进度都存放在视图之外，换成另一套外壳后原样复用。

播放器在两种宽度下是同一个对象，只是宿主容器不同：紧凑宽度用全屏容器，常规宽度用内联容器。两者之间切换只更换宿主，不重建解码管线，否则每次切全屏都要重新起播，与「拖动就出画」的体验目标冲突。

网格采用自适应最小宽度（160 点）而非固定列数，列数随宽度自然变化。

### D13 数据源抽象为字节源，验证按能力分层

解封装层不直接依赖 SMB，而是依赖一个字节源协议：能报长度、能按偏移读、能顺序读。SMB 与本地文件是它的两个实现，播放内核本身无从分辨。

这个抽象不是为了架构好看，而是为了**把可自动化的部分从必须人工的部分里切出来**：

| 验证对象 | 环境 | 手段 | 是否需要人工 |
| --- | --- | --- | --- |
| 解封装、解码、音画同步、跳转逻辑 | 模拟器 | 本地样本，引擎级无 UI 驱动 | 可断言，可回归 |
| 字幕渲染、样式与字体回退 | 模拟器 | 本地样本 + 截图比对 | 可断言 |
| 网格布局、标题解析、缓存淘汰 | 模拟器 | 单元测试与预览 | 可断言 |
| SMB 连接、认证、重连、地址解析 | 真机 | 对着真实共享操作 | 必须人工 |
| 首帧时延、拖动时延、吞吐、功耗 | 真机 | 秒表与实测记录 | 必须人工 |

这样做的直接收益是：播放内核的绝大多数缺陷可以在模拟器里、用几十 MB 的样本、几秒钟跑一遍就发现，而不必每次都走到真机、连上共享、拖到某个时间点去复现。

样本用 `ffmpeg -ss ... -t 30 -c copy` 从真实库中截取，保留原始编码与字幕轨，不重编码，因此与线上素材同构。

### D14 统一日志门面，关键路径必有打点

不用 `print`，也不各处散落 `os.Logger`。统一走一个 `Log` 门面，按分类区分：`app` / `smb` / `demux` / `render` / `subtitle` / `thumbnail`。级别三档，`debug` 默认关闭、可在诊断页开启。

必须打点的位置，按排查时最想看到的信息来选：

| 分类 | 打点内容 |
| --- | --- |
| `smb` | 地址归一化结果、名称解析耗时与结果、TCP 连接、认证结果、共享枚举耗时与条目数、每次读取的偏移/长度/优先级/等待与执行耗时、心跳、重连次数与退避间隔、错误归类 |
| `demux` | 打开文件、流信息（轨道清单与编码）、`av_seek_frame` 的目标时间与落点关键帧、解码至目标帧的耗时、是否精确命中、包队列水位 |
| `render` | 首帧呈现时刻、主时钟速率变化、A/V 偏差采样、显示层 flush 与重建 |
| `subtitle` | 轨道发现结果与外挂匹配情况、选中轨道、字体回退、渲染事件数 |
| `thumbnail` | 命中缓存 / 抽帧成功 / 失败原因 |

隐私约束：**绝不记录密码与凭据原文**，用户名可记；共享内的文件路径只记录末两级。

日志同时写入 OSLog 与一个 2000 条的内存环，App 内提供诊断页可查看、按分类过滤、复制导出。这样复现问题时不必连 Mac 抓 Console。

## 界面设计基线

参照主流视频 App（Apple TV、Infuse、Netflix）的简洁风格，不做「功能演示页」式的界面：

- **浅色为主**：媒体库用系统浅色底（`secondarySystemBackground` 卡片 + 细描边），跟随系统外观；只有播放页是深色，因为画面本身占据整屏。不强行统一成深色。
- **海报网格**：2:3 竖版单元格，标题两行截断，只显示必要信息（名称；文件额外给体积）。分区用留白而不是分割线或卡片边框。
- **极简框架**：导航栏只在标题与返回，不放多余按钮；设置、诊断这类入口收进二级菜单。
- **播放页全屏沉浸**：默认无控件，点按唤出；控件是底部一条半透明渐变，包含时间、进度条、播放/暂停与 ±10 秒，3.5 秒无操作自动淡出。
- **状态要有反馈但不打断**：加载用骨架或轻量指示，错误用一行可读文案，不弹模态框。
- **iPad 优先**：iPad 是主要场景，列数随可用宽度自然增加（当前 6 列 @11 寸竖屏），不做「手机界面放大」。

## Risks / Trade-offs

- **主机名解析在 iOS 上不完全可靠**：NetBIOS 短名依赖 mDNS/DNS 配置，企业网络下 `.local` 也可能被屏蔽。→ 错误提示明确区分解析失败与连接失败，并保留"改用 IP"的引导；连接表单记录最近一次成功的地址形式。
- **FFmpeg 构建是最大不确定性**：iOS 27 SDK 与旧构建脚本可能冲突，libass 依赖链（freetype/fribidi/harfbuzz）交叉编译易出错。→ 作为第一个 spike 验证，产出一个能解一帧的最小工程再继续；失败时回退到社区重编译产物。
- **音频输出与主时钟的锁序**：`AVAudioPlayerNode` 的方法内部会取引擎锁。若在持有音频输出锁时读播放位置，就会与「先停播放器（引擎锁）再清状态（输出锁）」的重置路径形成锁序反转，跳转时必然死锁。→ 读播放位置一律在锁外先取，重置先 `stop` 再清状态。
- **音画同步做不好会直接毁掉体验**：这是整套方案唯一的「难」点。→ 先做纯音频播放通路（不接 UI），用可听可测的方式验证时钟稳定性，再叠加画面。
- **模拟器不代表真机的解码行为**：模拟器中的 VideoToolbox 可能走软件回退，10-bit HEVC 与 HDR 的表现也可能与设备不符。→ 模拟器只判「解出的帧数、时间戳、字幕事件是否正确」，色彩、流畅度与功耗一律在真机复核；不把模拟器的帧率当作性能依据。
- **显示层进入需要刷新的状态**：iOS 在中断、后台切换、解码异常后会置位 `requiresFlushToResumeDecoding`，此时画面冻结。→ 监听失败通知，重建显示层并重新灌入参数集。
- **大屏下视图重新附着会让显示层失效**：内联与全屏切换、分栏宽度跳变都会把显示层从窗口摘下再挂回，画面可能变黑。→ 把显示层实例与播放器对象绑定而非与视图绑定，视图迁移时只转移父图层，并在重新附着后检查层状态、必要时重灌当前帧。
- **两套导航结构容易出现状态分叉**：紧凑与常规宽度各有一套外壳，容易在其中一套里遗漏某项状态。→ 状态只存放在视图之外的单一模型里，两套外壳都是它的纯投影，切换时不写回业务状态。
- **SMB 吞吐可能撑不住高码率**：24 MB 预读窗口按 1 Gbps 设计，实际 Wi-Fi 可能只有其三分之一。→ 窗口与读块大小自适应；实测码率超过链路能力时给出明确提示而非无声卡顿。
- **libass 逐帧重绘在 4K 下开销可观**：→ 只在事件变化时重绘，并对同一事件缓存位图。
- **真机调试的签名周期**：免费账号 7 天过期，会打断长周期开发。→ 使用付费账号或建立固定的重签流程。
- **许可证**：AMSMB2 与 FFmpeg 均为 LGPL。仅自用侧载无影响；若考虑分发，需改为动态链接并附源码获取方式。
- **ASS 字体缺失导致排版错乱**：字幕组常依赖专用字体。→ 内置一份中文字体子集兜底，同时优先使用容器内的字体附件。

## Migration Plan

全新工程，无历史数据与兼容负担。按可独立验证的里程碑推进，每阶段结束都能真机跑通一个完整场景：

1. 会话与媒体库：能连、能浏览、能看封面；两种宽度结构都在 iPad Air 与 iPhone 上跑通。
2. 播放通路：先音频后画面，再合流并校准同步。
3. 字幕：轨道发现、样式渲染、切换与调整。
4. 打磨：续播、后台、画中画、内联与全屏互转、错误恢复。

## Open Questions

- 库中 4K 与高码率素材的实际占比，以及真机 Wi-Fi 下的可持续吞吐，需在第一阶段用真实文件实测后再决定预读窗口的默认值。
- 分栏切单栈的宽度阈值取多少合适，需在 11 英寸 iPad Air 与 iPhone 上实际体验后确定，而不是照搬系统默认值。
- 字幕字号与偏移的默认值是否需要按屏幕尺寸分档，留待真机观感确定。
- 是否要在连接页提供局域网自动发现（Bonjour 的 `_smb._tcp`），让用户从列表里挑主机而不用手输名称。这不影响现有地址解析路径，可后置。
